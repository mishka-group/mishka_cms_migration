# Changelog for MishkaCmsMigration 0.0.1

- Initial version: [mishka.tools/cms](https://mishka.tools/cms)
- The project is set up like `mishka_blog` and `mishka_document`: the Mix package, an OTP application with no plugin yet, an Ash domain with no resource yet, the standalone test harness and a smoke test. It runs on `mishka_cms_core` 0.0.4, `mishka_gervaz` 0.0.3 and `mishka_installer` 0.1.15 from Hex, on Erlang 29.1.2 and Elixir 1.20.5
- CI runs the build, format check, `deps.audit` and the tests against PostgreSQL 18; `hex.audit` reports to code scanning every day; a `v*` tag builds the Hex package and the compiled ebin for a GitHub release
- A run (`MishkaCmsMigration.MigrationRun`) is one move of a site's content: its source, the host it reads from, how it connects, with the source's secret kept only sealed as core keeps a `:secret` setting and cleared once the run ends, and the admin's choices (`MishkaCmsMigration.Options`: authors, pages, post addresses, comments). It moves `:pending` → `:dry_running` → `:dry_run` → `:importing` → `:done`, or `:failed`, through its own actions; a step asked for out of order is refused. It is a site's own: reading, creating and starting one takes `admin:dashboard:migration` (`admin:api:migration` over the API), a master reaches every site and a site user only its own
- An item (`MishkaCmsMigration.MigrationItem`) remembers, per site, source host, kind and source id, the CMS row it was written to, when that row last changed as the migration left it, the item's hash and modified time on the source, and what the last run did with it and why. A run counts the items it was the last to touch
- A source is a Mishka Installer plugin on `migration:sources` behind `MishkaCmsMigration.Source` (connect, list a kind page by page, fetch one, normalize); each kind of item is written by a target, a plugin on `migration:targets` (`MishkaCmsMigration.Target`) that names an existing CMS resource and its create and update actions, so the extension adds no write path. Every source hands over the same normalized item (`MishkaCmsMigration.Item`)
- A dry run (`DryRunWorker`) reports what an import would create, update and skip, and why, writing nothing; an import (`ImportWorker`) writes each item through its target as the admin who pressed Import. Both run on the `migration` queue, one job per site at a time, broadcast their progress page by page over PubSub (`MishkaCmsMigration.Pipeline.topic/1`) and save their report on the run (`MishkaCmsMigration.Report`). Running again updates what the source changed, skips what it did not, and never overwrites a row an admin changed in the CMS or brings back one they deleted. A row the CMS refuses is recorded as failed with the CMS's reason, and the run goes on
- An import fires `migration:content:convert` for each block or shortcode the source could not convert, `migration:item:before_import` for each item about to be written (a plugin may change, skip or take it) and `migration:import:finished` with the report (`MishkaCmsMigration.Events`)
