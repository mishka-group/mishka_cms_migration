# Changelog for MishkaCmsMigration 0.0.1

- Initial version: [mishka.tools/cms](https://mishka.tools/cms)
- The project is set up like `mishka_blog` and `mishka_document`: the Mix package, an OTP application, the Ash domain with its two resources (runs and their items), the standalone test harness and its tests. It runs on `mishka_cms_core` 0.0.5-alpha.2, `mishka_gervaz` 0.0.3 and `mishka_installer` 0.1.15, on Erlang 29.1.2 and Elixir 1.20.5. It is not on Hex yet
- CI runs the build, format check, `deps.audit` and the tests against PostgreSQL 18; `hex.audit` reports to code scanning every day; a `v*` tag builds the Hex package and the compiled ebin for a GitHub release
- A run (`MishkaCmsMigration.MigrationRun`) is one move of a site's content: its source, the host it reads from, how it connects, the admin's choices (authors, pages, post addresses, comments, a `sub_field` of the run's own guardedstruct, read with their defaults through `MigrationRun.Options`) and the source's facts (`extra`). The source's secret is kept only sealed, as core keeps a `:secret` setting, from the run's creation until it ends; a secret that can no longer be opened fails the run. A run of a source that is not installed is refused when it is created
- A run moves `:pending` → `:dry_running` → `:dry_run` → `:importing` → `:done`, or `:failed`, through its own actions; a step asked for out of order is refused. An admin ends a run that is not done with `:cancel` (`:cancelled`): its job is cancelled and its secret cleared, so the site can start another, and a job already walking stops at its next page. A failed run keeps why in `reason`, the word an item uses. Its job saves its progress page by page through `:record_progress`, and the run's Ash notifier broadcasts it; no broadcast carries the run's connection or secret
- It is a site's own: reading, creating, starting and cancelling one takes `admin:dashboard:migration` (`admin:api:migration` over the API); a master reaches every site and a site user only its own. Installing the extension on a site from the CMS's installer creates both names, so a site's admin can be granted them; it takes `admin:dashboard:runtime:site`, on the installer's own site
- An item (`MishkaCmsMigration.MigrationItem`) remembers, per site, source host, kind and source id, the CMS record it was written to, when that record last changed as the migration left it, the item's hash and modified time on the source, the source's fields the CMS has no home for (`extra`), and what the last run did with it and why. Several sources can move into one site: two hosts' items never meet, and the second to claim an address the first took is reported, never written over it
- A source is a Mishka Installer plugin on `migration:sources` behind `MishkaCmsMigration.Source` (connect, list a kind page by page, normalize, and `extra/1` for its facts, `%{}` unless the source says more), listing its kinds in the order they are imported; each kind of item is written by a target, a plugin on `migration:targets` (`MishkaCmsMigration.Target`) that names an existing CMS resource and its create and update actions, so the extension adds no write path. Which are installed is read from Mishka Installer's own registry, so a stopped plugin is not used. A target whose resource has no UUID `:id`, no `updated_at` `update_timestamp` or not those actions does not compile. Every source hands over the same normalized item (`MishkaCmsMigration.Source.Item`). No source or target ships yet; WordPress is planned as the first source
- A dry run (`DryRunWorker`) plans what an import would create, update and skip, and why, writing nothing and asking no plugin; an import (`ImportWorker`) writes each item through its target as the admin who pressed Import, the CMS record and its item in one transaction. Both run on the `migration` queue, one job per site at a time and an hour an attempt, and save their report on the run (`MishkaCmsMigration.Report`: every item counted, the last 1,000 listed, reasons in the CMS's own words). Running again updates what the source changed, skips what it did not, and never overwrites a record an admin changed in the CMS or brings back one they deleted. A source id listed twice in a kind is written once
- An item the CMS refuses, or that a source, a plugin or a target raises on, is recorded as failed with the reason, and the run goes on; so is an item whose skip or failure cannot be recorded. A source that cannot connect or list, raises outside an item, or never ends its cursors fails the run on the job's last attempt; a last attempt Oban stops at its timeout or that crashes fails its run through Oban's own telemetry
- An import fires `migration:content:convert` for each block or shortcode the source could not convert, `migration:item:before_import` for each item about to be written (a plugin may change it, or skip it with `outcome: :skipped` and a reason) and `migration:import:finished` with the report (`MishkaCmsMigration.Events`). The first two fail closed: an item is skipped as `plugins_failed` when one of their plugins raised, and as `plugins_cannot_run` while one is not loaded
